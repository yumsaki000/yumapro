> 2026-09-28 受領。先方が使っているGoogleスプレッドシートをExcelで書き出したもの（36シート、約3MB）。
> 個人情報（顧客598人、出禁リスト）を含むため、ファイル自体はリポジトリに入れない。ここには構造と件数だけを書く。

## 今の運用の流れ

1. **顧客リスト本体は「声掛けリスト」**（598人）。名前・カタカナ・性別・紹介者・集客媒体・仕事内容・クルー状況・わくMe進捗・備考を持つ
2. **申込はGoogleフォーム1本**。回はフォーム内の選択肢で選ぶ。選択肢は「Googleフォーム項目」シートから自動で反映（5分後）
3. フォームの回答は「リスト統合版」で声掛けリストと突き合わせ（名前で照合）
4. **回ごとに「集客リスト」テンプレートをコピー**して1シート作る。598人全員が並び（FILTERで声掛けリストを引く）、その回の声かけ担当・進捗・入金・LINE・同意書を記入する
5. 回のシート上部で、スタッフ別の「声かけ数・紹介数・参加確定数・入金確定数」、料金ごとの人数と合計金額、男女比を自動集計
6. **出禁リスト**（52件）。申込フォームで条件が一致したら警告メールを送る仕組みがある。報告用のフォームもある
7. 「イベントカレンダー」の内容をGoogleカレンダーに反映
8. 一部の回（運動会・リトリート）は、別の「運用ファイル」と1時間ごとに同期している
9. 集計用に「参加イベント集計」「集計結果」（1人ごとの参加回数・支払合計）、「重複リスト」（名前が一致する人）がある

## 設計に効くこと

1. **名寄せの鍵は電話番号**。フォームでは電話が必須でメールは任意（5%しかない）。`docs/data-intake.md` の照合順（メール→電話）は、電話→メール→名前に変える
2. **集客は声かけと紹介が中心**。知り合い・他イベントで8割近く。こくちーずプロ経由は5人だけで、こくちーずは今ほぼ集客に効いていない
3. **女性が少ない**。顧客の37%。大きい回は男性中心で、女子会はシート上の参加が各回1〜4人。女子会を強化したいという方針と合う
4. **回ごとの進捗は申込の前から始まる**。「声掛け中 → 参加確定／不参加」。アプリの申込には、声をかけた段階（申込前）の状態も要る
5. **スタッフ別の集計を大事にしている**。誰が何人に声をかけ、何人が参加・入金したか
6. **参加費は人によって違う**（5,000／4,000／3,000／2,000円、リトリート30,000円）。1回に料金が複数ある。クルー（MINATOのメンバー）は参加費が割引になる（2026-09-28 Yumaさんより）。ほかの料金差の理由は確認中
7. **参加確定の条件に同意書**。ほかにLINE追加の確認欄がある
8. **形式は4つより多い**。朝活、ユメカタリバ、ビジョンボード会、リトリート、女子会、お花見、運動会、文化祭、お好み焼き会、餃子会、パートナーシップ、忘年会、マルシェ。オンラインとオフラインがある。形式は管理画面で増やせる作りにする
9. **顧客に持っている項目が多い**：仕事内容、紹介者、クルー状況（加入・脱退日）、わくMe進捗。個人情報を最小限にする方針と照らして、残すものを決める
10. **出禁チェックが要る**。申込時に一致したら運営に知らせる。証拠画像のリンクなど、扱いに特に注意が要るデータ
11. **Apps Scriptによる自動化がすでにある**（フォームの選択肢の更新、カレンダー連携、出禁の警告メール、運用ファイルとの同期）。アプリで置き換える対象

## 設計への反映（ヒアリングの回答を見てから）

- 顧客：性別、紹介者、最初の集客媒体、わくMeの状況、出禁の印を足すか。クルーかどうか（加入日・脱退日）は料金に効くので持つ
- 回：一般料金とクルー料金を持つ
- 申込：「声掛け中」「不参加」の状態、声かけ担当、紹介者、1人ごとの参加費、同意書、LINE追加を足すか
- 形式：管理画面で追加できるようにし、オンライン／オフラインを持つ
- 集計：スタッフ別の声かけ・参加・入金、男女比
- 移行：声掛けリスト598人、フォームの回答415件、回ごとのシートの進捗を参加履歴として取り込む

## Apps Script（「MINATO運用ツール」）

> 2026-09-28 にGoogle Drive経由でコードを確認（16ファイル・約1,600行、運営アカウントがオーナー）。
> コードには運営のメールアドレスやテスト用の個人情報が入っているため、リポジトリには入れない。
> 「運用ファイル」との1時間ごとの同期は、このプロジェクトには入っていない（別のスクリプトがあるとみられる）。

| 機能 | 動き | アプリでの扱い |
|---|---|---|
| フォームの選択肢の同期 | 1分ごとに「Googleフォーム項目」シートの有効な回を、申込フォームの「参加する日程」の選択肢に反映。表示は「【先頭挿入文】2026/1/10(土) 18:00〜20:00 イベント名【種別】」 | 掲示板と申込フォームが回のデータを直接使うので不要 |
| 出禁チェック | 申込フォームの送信時に出禁リストと照合。電話番号・メール・SNSのどれかが一致したら「確定」、氏名（空白除去・3文字以上）だけ一致したら「要確認」（フリガナ一致も表示）。スキップ印（◯）の人は除外。同じ電話番号の1分以内の再送信は無視。運営のメールに通知 | 同じ判定ルールで申込時にチェックし、運営に通知＋管理画面で印を付ける |
| スタッフ用フォームの転記 | 「声掛けリスト入力フォーム」「出禁リスト報告フォーム」の回答を各シートに転記 | 管理画面の顧客追加・出禁登録の画面にする |
| Googleカレンダー反映 | 「イベントカレンダー」シートの行から、運営のGoogleカレンダーに予定を作成・更新・削除（終了時刻が空なら2時間） | 回のデータから予定を出す。カレンダー連携の方法は要相談 |
| 参加の集計 | 手動の2段階。各回のシートから「LINE欄あり・進捗に"参加"を含む」人を集め、1人ごとの参加回数・支払合計を作る（番号＋名前で結合） | DBから自動で出るので不要 |
| 修復・リセット系 | 回のシートの数式（FILTER・IMPORTRANGE）やフィルタが壊れたときに作り直す、終わった回の数式を値に固定する、回のシートの入力欄を消す、時刻の分を補完する | DBなら数式が壊れないので不要 |

分かったこと：

- **数式やフィルタが壊れる前提の修復スクリプトが6本ある**。回ごとにシートをコピーして全員分をFILTERで引く作りが、保守の負担になっている
- **出禁チェックの判定ルールがはっきりしている**。アプリでもそのまま使える。照合にSNSアカウントを使うので、顧客にSNSアカウントの項目が要る
- **スタッフ専用のフォームが2つある**（声掛けリストへの追加、出禁の報告）。スタッフがスマホから登録できることが大事
- `onFormSubmit` という同じ名前の関数が2つのファイルにあり、Apps Scriptでは片方しか動かない。今どちらが動いているかは、設定されているトリガー次第（要確認）

## 収支表（「2026 … v13」）

> 2026-09-28 受領。売上・経費の管理表（Excel、10シート）。金額や個人名はここに書かない。

| シート | 中身 |
|---|---|
| 売上台帳 | 1件＝1行。日付・種類（サブスク／わくME／アパレル／カード／イベント／その他）・名前またはイベント名・売上・経費・利益（売上−経費）・備考・月（自動）。サブスクとわくMEの経費は決済手数料率から自動計算 |
| 売上集計・ダッシュボード | 売上台帳から種類×月で自動集計 |
| KPI目標・KPIダッシュボード | 月ごとの売上・経費・粗利の目標と実績。目標は別の「MINATO目標シート」から転記 |
| 2025年サマリー・2026年プール金 | 月ごとの売上・経費・利益と、プール金（純利益）の支出・残り |
| サブスク年間 | クルーの月ごとの入金一覧（名前・性別・紹介者・入会日・決済日・入金額） |
| わくME年間 | わくMEの月ごとの入金一覧 |
| イベント一覧 | 回ごとの売上・経費・利益・主催/参加メンバー |

分かったこと：

- **アプリからの書き出しは「売上台帳」の1行の形に合わせる**。日付＝開催日、種類＝イベント、名前＝「M月D日 イベント名」、売上＝集金合計、経費＝経費合計。イベントは1回＝1行で入っている
- **収支表の計算は「売上 − 経費 = 利益」**。要件にある「主催分」の欄はない（ヒアリング 5-4 で確認）
- **クルー（サブスク）の加入者と入金は収支表で管理**している。アプリでクルー料金を当てはめるには、クルーの一覧をアプリにも持つ必要がある（ヒアリング 4-7）
- **わくMeは価値観カードの名前**（Yumaさんより）。ただし収支表では「わくME」が物販の「カード」とは別の種類で、サブスクと同じく月ごとの入金がある。カードを使った講座・認定などの加入ものがあるとみられる（ヒアリング 4-8）
- 物販（Tシャツ・価値観カード）もあるが、アプリの範囲外
